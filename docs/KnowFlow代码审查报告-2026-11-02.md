## P1 · 向量索引双集合分裂：换过 embedding 提供方后，一部分文档对检索「不存在」

**证据**
- `vector_store_service.py` 按 `index_name` 分集合：哈希 → `knowflow_chunks`，DashScope → `knowflow_chunks_dashscope_text_embedding_v3`；`search()` 只查当前 active 的那一个集合。
- `embedding_service.py` 的 `ResilientEmbeddingService` 在主提供方失败时降级哈希、恢复后自动切回——只影响**新写入**走哪个集合，已写入的 chunk 不迁移、不重嵌。

**触发场景**（不需要极端条件）
1. 配了 key 一段时间，文档都进了语义集合；
2. 某天 key 失效/欠费，降级期上传的文档进了哈希集合；
3. key 恢复、切回语义集合后，第 2 步的文档在向量通道里**永远搜不到**（词法通道还在，所以表现是「向量召回莫名其妙缺一块」，极难察觉）。反向顺序同理。

**现状的补救与缺口**
- 有手动补救：每 KB 的 `rebuild-index`（全量重解析 + 重嵌入），但它同步执行、大库很慢，而且**没有任何地方提示用户「你需要重建」**——状态接口只报当前集合名，不报另一个集合里还躺着多少 chunk。
- `search()` 里还有一条启发式：active 集合为空且 fallback 集合非空时，全局切到 fallback。它有 warning 日志，但状态接口看不到「为什么在 fallback」，与模式可见性叠加后更难解释。

**与在途方案的关系**
- 方案的 T1.4（embedding 模式明示）解决的是「现在是不是语义检索」，不解决「数据是不是分裂」。建议在 T1 里增补一张 S 级小卡：health/status 暴露**两个集合各自的 chunk 数**，并在非 active 集合非空时给出 `index_stale` 类标记 + 重建入口提示。
- 不建议做双集合联合检索：哈希分数与语义余弦分数不可比，硬融会污染 T1 基线。

## P2 · 处理事务回滚后，向量可能短暂「先于数据」被检索命中

`document_processing_service.process_document_record` 先 `vector_store_service.add_chunks()`（Chroma 已落盘），再 `db.commit()`。提交失败时靠 except 分支补偿删向量；若补偿也失败（已记日志），孤儿向量要等**下次启动**的 `reconcile_orphan_vectors` 才清理。在这之前，向量通道的命中内容直接取自 Chroma、不回查 SQLite，所以一个最终标记为 failed 的文档，其内容仍可能出现在问答引用里。

概率低、窗口有限，但修复便宜：`search_hybrid` 本来就持有 db 会话，对向量命中按 chunk_id 做一次存在性过滤即可。或者明确接受并写入文档，二选一，别留成隐性行为。

## P3 · 边角清单（不阻塞 T1/T2，顺手时处理）

1. **词法通道单字盲区**：`lexical_search.to_search_text` 只产 bigram——单个汉字的查询（以及正文中的单字信息）产不出检索词，词法通道直接空手。混合模式有向量兜底；纯 lexical 或哈希降级期单字查询会明显弱。改法：索引与查询同步加 unigram，`search_text` 是落盘字段，需走已有的 backfill 迁移路径。
2. **Markdown front matter 误判**：`_parse_markdown_structure` 的 setext 规则会把 `---\ntitle: x\n---` 里的 `title: x` 当成二级标题。T2 动解析层时顺手跳过 front matter 即可。
3. **空章节生成「只有标题」的 chunk**：`split_text_structured` 对无正文章节用标题充当内容。标题词可检索是优点，但这类 chunk 可能挤占 RRF 名额、被本地摘录模式当成答案。建议 T1 评测时专门观察，先不改行为。
4. **上传只验扩展名**：改名文件会走到解析器才失败（有 failed 状态兜底，可接受）；docx/pptx 作为 zip 没有解压后体积上限，50MB 上限只管压缩包本身。本地单用户风险低，备忘即可。
5. **弃用警告**：`HTTP_413_REQUEST_ENTITY_TOO_LARGE` 在新版 Starlette 已更名为 `HTTP_413_CONTENT_TOO_LARGE`，升级 fastapi 时顺手改（本地测试已见此 warning）。
6. **前端正式应用放在 `src/demo/` 目录**：历史命名，与功能无关，但会持续误导新读者。
7. **管理端 export / clear-all 无鉴权**：与 `SECURITY.md` 的本地单用户边界一致，compose 也只绑 `127.0.0.1`，现状自洽。仅提醒一句：将来任何「顺手开局域网访问」的动作，都会同时暴露这两个接口。

## 做得好的地方（点名，供后续改动时保持）

- **生成侧防注入转义**是全仓最扎实的一块：`rag_service._escape_content` 把 `</source>` 伪造、 `[资料 N]` 引用伪造、「用户问题：」标题伪造三类都堵了，系统提示词同时声明资料不可信。T3 摄入侧筛查正是把同一标准补到索引侧，方向一致。
- **分数语义较真**：`hybrid_search.py` 把 vector / rrf_fused / lexical 三种 scale 的含义写进注释，并用 `LEXICAL_ONLY_DISCOUNT` 防「单命中必过阈值」的漂移——这种细致很少见，也是 T1 评测能直接复用的资产。
- **一致性闭环**：FTS5 外部内容表 + 触发器同步、版本化幂等迁移（`schema_migrations`）、启动时中断文档恢复 + 孤儿向量对账、处理失败的补偿删除、重试前清残留，都有对应测试。
- **CI 完整**：ruff format/check + mypy + pytest 覆盖率 + pip-audit（忽略项逐条显式列出）+ GitHub Actions 全部按 SHA 锁定版本。
- **部署边界诚实**：无鉴权这件事在 `SECURITY.md` 和 `docker-compose.yml` 注释里明说，端口只绑本机——边界是设计选择，不是疏漏。

## 对在途升级方案（T1+T2，本轮已锁定）的审查意见

1. **顺序认同**：T1.4（模式明示）排在 T1.3（评测 CLI）之前是对的，否则基线数字自带歧义。
2. **建议增补一张卡**：即 P1 的「索引一致性可见」（双集合计数 + 待重建标记）。T1.3 的评测用临时 KB 建索引，不受存量分裂影响，但用户真实 KB 的体感问题不会被 T1–T4 顺带解决，越晚补越被动。
3. **T1.3 的一个实现提醒**：评测 CLI 复用 `document_processing_service` 时，它写的是全局 `vector_store_service` 单例（真实 Chroma 目录）。方案风险登记已写明「一律临时目录」，执行时要确认向量目录同样可注入隔离，不只是 SQLite 用内存库。
4. **基线数字口径**：方案文档记「本地测试基线 176 passed」，实测是收集 176 条、通过 175、跳过 1（frontend/dist 未构建，CI 后端任务同样会跳过这一条）。归档 T1.5 基线报告时按实测口径写，避免以后对不上账。
5. T2.1 设为门禁式任务（样本可得率不足就停）、T2.7 要求 placebo 结论「不许只写通过」——这两处都很好，保持。
